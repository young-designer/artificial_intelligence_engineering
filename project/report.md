# Отчёт по проекту

## Паспорт

- Название: «Сервис прогнозирования риска срыва доставки заказа»
- Домен: табличная бизнес-задача
- Предметная область: e-commerce, last-mile delivery, операционный мониторинг заказов
- ML-задача: бинарная классификация `is_late_delivery`

## Постановка задачи

Цель проекта — помочь операционному менеджеру службы доставки заранее находить заказы, которые с высокой вероятностью будут доставлены с опозданием. Сервис получает параметры заказа, маршрута, курьера и текущих условий доставки, а затем возвращает вероятность срыва срока и уровень риска.

Практический сценарий:

- менеджер видит заказы с высоким риском и может переназначить курьера;
- служба поддержки заранее предупреждает клиента;
- логистическая команда использует агрегированные риски для контроля нагрузки склада и курьеров.

В терминах ML это бинарная классификация. Положительный класс `1` означает, что заказ будет доставлен позже обещанного срока. Для такого сценария особенно важен `Recall`: лучше заранее заметить больше потенциально проблемных заказов, чем пропустить критичную задержку. Поэтому финальный выбор модели делался по `F1`, а `Recall` рассматривался как ключевая вспомогательная метрика.

## Данные

Источник данных — синтетический датасет `data/delivery_orders_synthetic.csv`, который создаётся скриптом `src/data_generation.py`. Синтетика выбрана осознанно: она не содержит персональных данных, не нарушает коммерческую тайну и позволяет воспроизвести проект после чистого клона.

В датасете 6500 заказов. Целевая переменная:

- `is_late_delivery` — факт срыва доставки: `0` или `1`.

Ключевые признаки:

- числовые: `order_value`, `items_count`, `delivery_distance_km`, `promised_hours`, `warehouse_backlog`, `courier_experience_months`, `courier_load_today`, `historical_late_rate`, `address_quality_score`, `route_complexity`;
- категориальные: `delivery_type`, `region_type`, `payment_type`, `package_size`, `traffic_level`, `weather_condition`, `dispatch_shift`;
- бинарные: `is_weekend`, `is_holiday`, `fragile_item`, `requires_call_before_delivery`.

Генератор устроен так, чтобы риск задержки рос при плохой погоде, сильном трафике, дальнем маршруте, большой загрузке склада, маленьком опыте курьера, низком качестве адреса и срочном типе доставки.

## EDA

Основной EDA лежит в `notebooks/01_eda_and_experiments.ipynb`.

Ключевые наблюдения:

- доля опоздавших доставок: `40.52%`;
- средняя дистанция доставки: `12.91` км;
- средняя загрузка склада: `6.18` заказов в очереди;
- средняя сложность маршрута: `3.77` по шкале от 1 до 10;
- при `storm` доля задержек около `59.7%`, при `clear` — около `35.6%`;
- при `severe` traffic доля задержек около `60.4%`, при `low` — около `31.9%`;
- `same_day` доставка значительно рискованнее: около `74.8%` задержек против `10.9%` для `scheduled`;
- в выходные риск выше: `45.5%` против `38.5%` в будни.

Эти зависимости соответствуют предметной логике и помогают объяснить поведение модели.

## Эксперименты

Обучение реализовано в `src/train.py`. Конфигурация лежит в `configs/train_config.yaml`.

Пайплайн:

1. генерация синтетических данных;
2. train/test split `80/20` со стратификацией по целевой переменной;
3. обработка числовых, категориальных и бинарных признаков через `ColumnTransformer`;
4. обучение нескольких моделей;
5. сохранение лучшей модели и метаданных.

Сравнивались:

- `LogisticRegression`;
- `RandomForestClassifier`;
- `GradientBoostingClassifier`.

Результаты на тестовой выборке:

| Модель | Accuracy | Precision | Recall | F1 | ROC-AUC |
|---|---:|---:|---:|---:|---:|
| LogisticRegression | 0.7638 | 0.6877 | 0.7647 | 0.7242 | 0.8365 |
| RandomForestClassifier | 0.7385 | 0.6632 | 0.7211 | 0.6909 | 0.8195 |
| GradientBoostingClassifier | 0.7592 | 0.7238 | 0.6565 | 0.6886 | 0.8237 |

## Выбор финальной модели

Финальной выбрана `LogisticRegression`.

Причины:

- лучший `F1 = 0.7242`;
- лучший `Recall = 0.7647`, что важно для раннего обнаружения задержек;
- хороший `ROC-AUC = 0.8365`;
- модель быстро обучается, быстро работает на инференсе и проще объясняется.

`GradientBoostingClassifier` дал лучшую `Precision`, но заметно проиграл по `Recall`: в учебном бизнес-сценарии это хуже, потому что сервис будет пропускать больше проблемных доставок.

## Архитектура сервиса

Сервис реализован на FastAPI в `src/service.py`.

Эндпоинты:

- `GET /` — краткая карта сервиса;
- `GET /health` — проверка готовности и имени загруженной модели;
- `GET /model-info` — метрики финальной модели и баланс классов;
- `GET /metrics` — базовые текстовые метрики;
- `POST /predict` — прогноз риска задержки для списка заказов.

`/predict` принимает JSON вида:

```json
{
  "orders": [
    {
      "delivery_type": "express",
      "region_type": "suburb",
      "payment_type": "prepaid",
      "package_size": "large",
      "traffic_level": "high",
      "weather_condition": "rain",
      "dispatch_shift": "day",
      "is_weekend": true,
      "is_holiday": false,
      "fragile_item": false,
      "requires_call_before_delivery": false,
      "order_value": 12990.0,
      "items_count": 3,
      "delivery_distance_km": 24.2,
      "promised_hours": 18.0,
      "minutes_since_order": 420,
      "warehouse_backlog": 11,
      "courier_experience_months": 12.0,
      "courier_load_today": 10,
      "historical_late_rate": 0.26,
      "previous_failed_deliveries": 1,
      "address_quality_score": 0.62,
      "route_complexity": 6.4,
      "customer_priority_score": 2
    }
  ]
}
```

Ответ содержит бинарный прогноз, вероятность, риск-сегмент и рекомендуемое действие.

## Наблюдаемость, конфигурация и безопасность

Наблюдаемость:

- логируются HTTP-запросы, статус-коды и latency;
- `/metrics` отдаёт счётчики запросов, ошибок, количества обработанных заказов и uptime;
- `/health` проверяет, что модель загружена.

Конфигурация:

- параметры обучения лежат в `configs/train_config.yaml`;
- пути к модели, окружение и уровень логирования задаются через `.env.example`;
- реальные `.env` добавлены в `.gitignore`.

Безопасность:

- персональные данные не используются;
- датасет синтетический;
- токены, пароли и реальные секреты в проект не добавлялись.

## Тестирование

Тесты лежат в `tests/test_service.py`.

Проверяется:

- успешный `/health`;
- рабочий `/predict` на валидном payload;
- валидация некорректных входных данных;
- наличие `/metrics`.

Команда:

```bash
python -m unittest tests/test_service.py
```

## Ограничения и дальнейшая работа

Ограничения:

- данные синтетические и не покрывают все реальные паттерны логистики;
- нет интеграции с картами, реальными пробками и трекингом курьеров;
- пороги `medium/high` заданы экспертно;
- сервис не хранит историю запросов.

Дальнейшие шаги:

- подобрать decision threshold по стоимости ошибок;
- добавить объяснения предсказаний через feature importance или SHAP;
- подключить реальные обезличенные события доставки;
- добавить Prometheus/Grafana вместо простого текстового `/metrics`;
- добавить CI для автоматического запуска тестов.

## Сценарий демонстрации

1. Показать структуру проекта и объяснить, где данные, код, модель и отчёт.
2. Запустить `python -m src.train` и показать таблицу метрик.
3. Запустить `uvicorn src.service:app --host 0.0.0.0 --port 8000`.
4. Открыть `http://localhost:8000/docs`.
5. Отправить `src/demo_request.json` в `/predict`.
6. Показать `/health`, `/model-info` и `/metrics`.
